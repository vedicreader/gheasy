core

Keep a project’s CI settings in .gheasy/config.json, and generate its workflow, git hooks, LFS rules and GitHub settings from them.

Setup & Imports

A test repository

The examples on this page run inside GheasyTestRepo, a throwaway Git repository whose origin remote is a local bare repository. Both are deleted when the with block ends.

import tempfile, shutil
class GheasyTestRepo:
    'Context manager: real temp git repo with initialized git and fake remote.'
    def __enter__(self):
        self._tmp = tempfile.mkdtemp()
        self.path = Path(self._tmp)
        # bare repo to push to
        self._bare = tempfile.mkdtemp()
        sp.run(['git', 'init', '--bare', self._bare], check=True, capture_output=True)
        self.remote = f'file://{self._bare}'
        sp.run(['git', 'init', str(self.path)], check=True, capture_output=True)
        sp.run(['git', '-C', str(self.path), 'remote', 'add', 'origin', self.remote], check=True, capture_output=True)
        sp.run(['git', '-C', str(self.path), 'config', 'user.email', 'test@test.com'], check=True, capture_output=True)
        sp.run(['git', '-C', str(self.path), 'config', 'user.name', 'Test'], check=True, capture_output=True)
        return self
    def __exit__(self, *a):
        shutil.rmtree(self._tmp, ignore_errors=True)
        shutil.rmtree(self._bare, ignore_errors=True)

Config

GheasyConfig is the contents of .gheasy/config.json as a Python object. Its app field holds the project name. envs holds one EnvConfig per place the app is deployed, such as prod or staging; each records the server’s host, the domain it serves, the branch that deploys there, and the app’s folder on the server. The remaining fields feed the generators further down. workflows and workflow_preset choose the CI jobs, test_cmd replaces pytest, deploy_cmd is the shell command a deploy job runs, extra_jobs holds custom jobs, env_schema decides which settings become secrets, and hooks and lfs set up the local repository.

add_env, set_lfs, set_hooks, set_workflows and add_job change the config and return it, so calls can be chained before save. load reads the file, and returns an empty config when there is none. from_pyproject starts a config named after the project in pyproject.toml.

Generators

The mk_* functions turn a config into the contents of a file and return it as text; the gh_* functions further down write the files.

mk_deploy_job adds one environment’s deploy job to a Workflow builder. The job waits for test, runs only for pushes to that environment’s branch, writes the DEPLOY_KEY secret out as an SSH key, adds the server to known_hosts, and then runs the deploy command. The command is the cmd you pass, or the config’s deploy_cmd; with neither, it prints a warning and adds nothing.

Workflow generation

mk_workflow builds the whole CI workflow for a config and returns it as YAML text, headed by a comment saying gheasy manages the file. Which jobs it includes is decided in three layers, each overriding the one before: the preset named in workflow_preset, the flags in cfg.workflows, and the keyword arguments you pass. A preset only switches on a language job: rust and go turn on the job of the same name, fastapi-react and nodejs turn on node, and python and fasthtml turn on nothing.

Flag Job What it runs
test test uv run pytest, or uv run followed by cfg.test_cmd
lint lint ruff check and ruff format --check
publish_pypi publish uv build and a PyPI upload, only when a release starts the workflow
docker_build docker builds the image and pushes it to GHCR
node frontend npm ci, npm run build and npm test
rust build cargo build, cargo test and cargo clippy
go build go build, go test and go vet
on_pull_request none runs the workflow on pull requests as well as pushes

The publish and docker jobs wait for test, so keep test on when you use them. The workflow runs on pushes to the branches named in cfg.envs, or to main when there are no environments. Each environment gets a deploy job from mk_deploy_job, and the custom jobs in cfg.extra_jobs are added last. gh_workflow writes the result to .github/workflows/gheasy.yml. Regenerate that file rather than editing it, because the next regeneration overwrites hand edits.

.gitattributes generation

.gitattributes tells Git how to treat files that match a pattern, and Git LFS needs one line there for every pattern it handles. mk_gitattributes writes those lines between # BEGIN gheasy-lfs and # END gheasy-lfs markers, so that gh_gitattributes can later replace just that block and keep any lines you added yourself. mk_hook wraps a command in a bash script between similar markers, # BEGIN gheasy-managed and # END gheasy-managed, for gh_hooks to install.

mk_dependabot writes a .github/dependabot.yml, the file that asks GitHub’s Dependabot to open pull requests when your dependencies have new versions. By default it checks pip packages and GitHub Actions every week.

Local Git setup

The next functions change files inside your checkout: hook scripts in .git/hooks/ and the LFS block in .gitattributes.

Git hooks

A git hook is a script Git runs at a fixed moment, such as pre-commit, which runs just before each commit and can stop it. gh_hooks installs hooks from a dict of hook name to command, where a command is a string or a list of lines. Without a dict it uses hooks from the config. It writes each script into .git/hooks/ between gheasy’s markers and makes it executable. Running it again replaces only the marked block, so anything you wrote above or below it stays.

nbdev_hook returns the usual command for an nbdev project, uv run --with nbdev nbdev-prepare, which exports, tests and cleans the notebooks before every commit. gh_githooks_pre_commit installs that command, or the one you pass, as the pre-commit hook.

Git never commits the contents of .git/hooks/, so these hooks stay on your machine and each new clone needs them installed once. gh_setup and GheasyRepo.new do that for you. When hooks have to be shared across many repositories, or are written in several languages, the pre-commit package is the better tool.

LFS and .gitattributes

Large binary files such as model weights and databases make a repository slow to clone, because every version stays in the history. Git LFS stores them on a separate server and commits a small pointer file in their place. gh_lfs runs git lfs install, then git lfs track for each pattern, and saves the patterns to the config. Without patterns it tracks a default list: *.db, *.onnx, *.bin, *.pt, *.pkl, *.safetensors, *.tar.gz, *.mp4 and *.parquet.

gh_gitattributes rewrites the gheasy block in .gitattributes from the patterns in the config and leaves every other line alone, so attributes you added yourself, such as *.sh text eol=lf, survive. Run it after changing the patterns in the config.

gh_lfs(['*.onnx', '*.db', '*.safetensors'])  # once per repository
gh_gitattributes()                           # after any change to the patterns in the config
# then: git add .gitattributes && git commit -m 'chore: update .gitattributes'

GitHub settings

The functions from here on change settings stored on GitHub, not files in your checkout.

Finding the repository and the token

gh_api works out which GitHub repository a checkout belongs to from the URL of its origin remote, and returns the owner, the repository name and a ghapi client bound to it. It raises ValueError when the remote is missing or does not look like owner/repo. gh_token returns the token you pass, or the GITHUB_TOKEN environment variable when you pass nothing.

Repository settings

Branch protection is a set of rules GitHub enforces on a branch, such as requiring an approving review or passing checks before a pull request can merge. gh_protect sets those rules for one branch: how many approvals are needed, whether a new push dismisses earlier approvals, which status checks must pass, whether administrators are bound by the rules too, and whether force pushes are allowed. gh_topics replaces the repository’s topics, the tags shown on its GitHub page, and lowercases each one because GitHub requires it. Both need a token whose owner is an administrator of the repository.

gh_protect('main',
    require_reviews=1,
    require_status_checks=['test', 'lint'],

Secrets and variables

GitHub Actions jobs read their settings from two stores. A secret is encrypted and hidden in logs; a variable is plain text. gh_secret sets one secret with gh secret set. With env='prod' it scopes the secret to the GitHub environment prod, so only jobs that deploy there can read it. gh_secrets_from_file sets every KEY=VALUE line of a file such as .env as a secret. Use gh_push_env when some values should be variables: it takes a dict and uses the config’s env_schema to choose, sending a key whose schema default is None to the secrets and a key with a string default to the variables. All three accept dry_run=True, which prints the gh commands instead of running them.

gh_deploy_key_setup uploads an SSH private key as the DEPLOY_KEY secret that the deploy jobs from mk_deploy_job use to reach the server. Two steps come first and are yours to do: create the key pair with ssh-keygen -t ed25519 -f deploy_key, and add the public key to the server’s ~/.ssh/authorized_keys.

These functions need the gh command line tool installed and logged in (gh auth login).

Lifecycle

Naming a repository

Functions that take a GitHub repository accept it in three forms: an owner/repo string, a GitHub URL such as https://github.com/owner/repo, or a local path whose origin remote points at GitHub. _resolve_gh_repo_input turns any of them into an (owner, repo) pair, and _git_branch reads the branch a checkout is on, falling back to main.

The pull request a branch belongs to

An editor’s status line wants to say whether the current branch has an open pull request on GitHub and how it stands. pr_context(path, branch) answers that. It returns the pull request’s number, title and link, the branch it targets (its base), whether it is a draft, GitHub’s merge state, how many commits the branch is ahead of the base and how many the base has gained since the branch split off, and the total, failing and pending checks on the branch’s latest commit. The answer is cached for a minute, because a status line asks far more often than a pull request changes.

pr_context never raises. When there is no open pull request, no GitHub remote, no token, or GitHub refuses the request, pr is None and note says why. The example below runs _checks, the part that counts checks, against a fake API.

Setting up a project

These are the main entry points, and all but gh_record_deploy are also gheasy commands. They read and write .gheasy/config.json and print what to do next.

gh_init writes a new config with one environment, replacing any config already there; without branch it uses the branch you have checked out. gh_add_env adds or replaces an environment and rewrites .github/workflows/gheasy.yml at once. gh_add_job stores a custom job, written as the dict you would put under jobs: in the YAML, for the next workflow build. gh_workflow writes the workflow file, and with a token it also commits the file to GitHub through the API. gh_status prints a table of the deploys recorded so far, and gh_ship runs gh_workflow and then gh_status. gh_record_deploy is the call a deploy job makes at the end to record which commit it shipped and when.

One-call setup

gh_setup is what you run once in a new project. It calls gh_init, writes the workflow with gh_workflow, and installs a pre-commit hook that runs uv run nbdev_prepare. Pass a hooks dict to install other hooks instead, or hooks={} to install none. After that, gh_add_env and gh_ship cover most changes.

gh_setup('myapp', '1.2.3.4', 'myapp.example.com',
         env_schema={'DB_URL': None, 'PORT': '8000'},
         workflows={'lint': True})
# writes .gheasy/config.json
# writes .github/workflows/gheasy.yml
# installs a pre-commit hook that runs: uv run nbdev_prepare

Later, to add a staging server that deploys from dev:

gh_add_env('staging', '5.6.7.8', 'staging.myapp.com', branch='dev')
gh_ship()  # rewrite the workflow and print the deploy table

Repository health

gh_check audits a repository against gheasy’s defaults and returns a list of findings. In the checkout it looks for gheasy’s pre-commit hook, for the LFS block in .gitattributes, and for a pyproject.toml that builds with hatchling. With a token it also asks GitHub whether the repository has topics and a .github/dependabot.yml. gh_apply then runs the fix of every finding that has one. dry_run=True lists the fixes without running them, and confirm=True asks before each. The local findings come with fixes; the GitHub ones only suggest what to run.

RepoFinding

Each finding is a RepoFinding. It has a level (ok, warn or error), a category such as hooks or lfs, a message, an optional function that fixes the problem, the command that fix stands for, and a link to documentation. Printing a finding shows a tick, a warning sign or a cross, then the category, the message and the suggested command. apply runs the fix, or prints the suggested command when there is no fix.

GheasyRepo

GheasyRepo holds a repository reference, a token and a local path, and runs the functions above with them. Creating one makes no API calls; it only parses the reference, which can be owner/repo, a GitHub URL, or a local path with a GitHub remote. check and apply are gh_check and gh_apply for that repository. create makes the repository on GitHub, under an organisation when the owner is not the signed-in user.

GheasyRepo.new scaffolds a whole project in one call. It creates the GitHub repository, clones it, pins the Python version with uv python pin, runs nbdev-new when the template is nbdev, converts pyproject.toml to hatchling, sets up LFS with the default patterns, installs the nbdev pre-commit hook, writes a workflow when you pass workflows, commits, pushes, and sets the topics. The gheasy gh-new command calls it.

Migration

pyproject.toml migration

gheasy expects projects to build with hatchling. gh_pyproject_to_hatchling rewrites pyproject.toml to do so. It sets [build-system] to hatchling and requires-python to >=3.11, points the wheel and the version number at the package folder named after the project, limits the source distribution to that folder, README.md and pyproject.toml, and removes any [tool.setuptools] section. It edits the file with tomlkit, which keeps your comments and formatting, and a second run changes nothing. dry_run=True only prints which file it would change.
