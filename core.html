core

Keep a project’s CI settings in .gheasy/config.json, and generate its workflow, git hooks, LFS rules and GitHub settings from them.

Setup & Imports

A test repository

The examples on this page run inside GheasyTestRepo, a throwaway Git repository whose origin remote is a local bare repository. Both are deleted when the with block ends.

import tempfile, shutil
class GheasyTestRepo:
    'Context manager: a temporary Git repository whose `origin` is a local bare repository. Both are deleted on exit.'
    def __enter__(self):
        self._tmp = tempfile.mkdtemp()
        self.path = Path(self._tmp)
        self._bare = tempfile.mkdtemp()
        sp.run(['git', 'init', '--bare', self._bare], check=True, capture_output=True)
        self.remote = f'file://{self._bare}'
        sp.run(['git', 'init', str(self.path)], check=True, capture_output=True)
        sp.run(['git', '-C', str(self.path), 'remote', 'add', 'origin', self.remote], check=True, capture_output=True)
        sp.run(['git', '-C', str(self.path), 'config', 'user.email', 'test@test.com'], check=True, capture_output=True)
        sp.run(['git', '-C', str(self.path), 'config', 'user.name', 'Test'], check=True, capture_output=True)
        return self
    def __exit__(self, *a):
        shutil.rmtree(self._tmp, ignore_errors=True)
        shutil.rmtree(self._bare, ignore_errors=True)

Config

GheasyConfig is the contents of .gheasy/config.json as a Python object. app holds the project name. envs holds one EnvConfig per place the app is deployed, such as prod or staging. Each EnvConfig records the server’s host, the domain it serves, the branch that deploys there, and the app’s folder on the server.

The other fields feed the generators further down. workflows and workflow_preset choose the CI jobs. test_cmd replaces pytest. deploy_cmd is the shell command a deploy job runs. extra_jobs holds custom jobs. env_schema decides which settings become secrets. hooks and lfs set up the local repository.

add_env, set_lfs, set_hooks, set_workflows and add_job change the config and return it. Chain the calls before you call save. load reads the file and returns an empty config when the file does not exist. from_dict ignores keys that are not config fields. from_pyproject starts a config named after the project in pyproject.toml.

Generators

The mk_* functions turn a config into the text of a file. The gh_* functions further down write the files.

mk_deploy_job adds the deploy job of one environment to a Workflow builder. The job waits for the test job when the workflow has one, and runs only for pushes to the branch of that environment. It writes the DEPLOY_KEY secret to ~/.ssh/id_rsa, adds the server to known_hosts, and runs the deploy command. The command is the cmd you pass, or the config’s deploy_cmd. With neither, mk_deploy_job prints a warning and adds nothing.

Workflow generation

mk_workflow builds the whole CI workflow for a config and returns it as YAML text, headed by a comment that says gheasy manages the file. Three layers decide which jobs it includes, and each layer overrides the one before: the preset named in workflow_preset, the flags in cfg.workflows, and the keyword arguments you pass. A preset switches on a language job only. rust and go turn on the job of the same name. fastapi-react and nodejs turn on node. python and fasthtml turn on nothing.

Flag Job What it runs
test test uv run pytest, or uv run followed by cfg.test_cmd
lint lint ruff check and ruff format --check
publish_pypi publish uv build and a PyPI upload, only when a release starts the workflow
docker_build docker builds the image and pushes it to GHCR
node frontend npm ci, npm run build and npm test
rust build cargo build, cargo test and cargo clippy
go build go build, go test and go vet
on_pull_request none runs the workflow on pull requests as well as pushes

The publish and docker jobs wait for test when it is on, and publish adds a release trigger to the workflow. The workflow runs on pushes to the branches named in cfg.envs, or to main when the config has no environments. mk_deploy_job adds a deploy job for each environment that has a deploy command. The custom jobs in cfg.extra_jobs are added last. gh_workflow writes the result to .github/workflows/gheasy.yml. With a token, it also commits the file to GitHub. Regeneration overwrites manual edits. Change the config and regenerate the file.

.gitattributes generation

.gitattributes tells Git how to treat files that match a pattern. Git LFS needs one line there for each pattern it handles. mk_gitattributes writes those lines between # BEGIN gheasy-lfs and # END gheasy-lfs markers. gh_gitattributes later replaces only the lines between the markers and keeps every other line. mk_hook wraps a command in a bash script between the markers # BEGIN gheasy-managed and # END gheasy-managed. gh_hooks installs that script.

mk_dependabot returns the text of a .github/dependabot.yml. That file asks GitHub’s Dependabot to open pull requests when your dependencies have new versions. By default it checks pip packages and GitHub Actions every week.

Local Git setup

The next functions change files inside your checkout: hook scripts in .git/hooks/ and the LFS block in .gitattributes.

Git hooks

A git hook is a script Git runs at a fixed moment, such as pre-commit, which runs just before each commit and can stop it. gh_hooks installs hooks from a dict of hook name to command, where a command is a string or a list of lines. Without a dict it uses hooks from the config. It writes each script into .git/hooks/ between gheasy’s markers and makes the script executable. Running it again replaces only the marked block. Anything you wrote above or below the block stays. When the path has no .git directory, gh_hooks prints a message and writes nothing.

nbdev_hook returns the usual command for an nbdev project, uv run --with nbdev nbdev-prepare. The command exports, tests and cleans the notebooks before every commit. gh_githooks_pre_commit installs that command, or the one you pass, as the pre-commit hook.

Git never commits the contents of .git/hooks/, so these hooks stay on your machine and each new clone needs them installed once. gh_setup and GheasyRepo.new do that for you. When hooks have to be shared across many repositories, or are written in several languages, the pre-commit package is the better tool.

LFS and .gitattributes

Large binary files such as model weights and databases make a repository slow to clone, because every version stays in the history. Git LFS stores them on a separate server and commits a small pointer file in their place. gh_lfs runs git lfs install, then git lfs track for each pattern, and saves the patterns to the config. Without patterns it tracks a default list: *.db, *.onnx, *.bin, *.pt, *.pkl, *.safetensors, *.tar.gz, *.mp4 and *.parquet.

gh_gitattributes rewrites the gheasy block in .gitattributes from the patterns in the config. It leaves every other line alone, including attributes you added yourself, such as *.sh text eol=lf. Run it after you change the patterns in the config. It prints a message and writes nothing when the config file is missing or has no LFS patterns.

gh_lfs(['*.onnx', '*.db', '*.safetensors'])  # once per repository
gh_gitattributes()                           # after any change to the patterns in the config
# then: git add .gitattributes && git commit -m 'chore: update .gitattributes'

GitHub settings

The functions from here on change settings stored on GitHub, not files in your checkout.

Finding the repository and the token

gh_api works out which GitHub repository a checkout belongs to from the URL of its origin remote, and returns the owner, the repository name and a ghapi client bound to it. It raises ValueError when the remote is missing or does not look like owner/repo. gh_token returns the token you pass, or the GITHUB_TOKEN environment variable when you pass nothing.

Repository settings

Branch protection is a set of rules GitHub enforces on a branch, such as requiring an approving review or passing checks before a pull request can merge. gh_protect sets those rules for one branch: how many approvals are needed, whether a new push dismisses earlier approvals, which status checks must pass, whether administrators are bound by the rules too, and whether force pushes are allowed. gh_topics replaces the repository’s topics, the tags shown on its GitHub page, and lowercases each one because GitHub requires it. Both need a token whose owner is an administrator of the repository.

gh_protect('main',
    require_reviews=1,
    require_status_checks=['test', 'lint'],
    dismiss_stale=True)

Secrets and variables

GitHub Actions jobs read their settings from two stores. A secret is encrypted and hidden in logs. A variable is plain text. gh_secret sets one secret with gh secret set. With env='prod' it scopes the secret to the GitHub environment prod. Only jobs that deploy to that environment can read it. gh_secrets_from_file sets every KEY=VALUE line of a file such as .env as a secret. Use gh_push_env when some values are variables. It takes a dict and uses the config’s env_schema to choose. A key whose schema default is None becomes a secret. A key with a string default becomes a variable. A key missing from the schema is skipped with a warning. gh_push_env raises FileNotFoundError when .gheasy/config.json does not exist. gh_secret, gh_secrets_from_file and gh_push_env accept dry_run=True, which prints the gh commands and does not run them.

gh_deploy_key_setup uploads an SSH private key as the DEPLOY_KEY secret that the deploy jobs from mk_deploy_job use to reach the server. Before you call it, create the key pair with ssh-keygen -t ed25519 -f deploy_key and add the public key to the server’s ~/.ssh/authorized_keys.

These functions need the gh command line tool installed and logged in (gh auth login).

Naming a repository

The ref parameter identifies a GitHub repository. It accepts an owner/repo string or a GitHub URL such as https://github.com/owner/repo. When ref is None, _resolve_gh_repo_input reads the owner and name from the origin remote of the checkout at path. It raises ValueError when it cannot parse ref. _git_branch returns the branch a checkout is on, or main when it cannot read the branch.

The pull request a branch belongs to

pr_context(path, branch) tells an editor’s status line whether branch has an open pull request on GitHub and how the pull request stands. It returns the pull request’s number, title and link, and the branch it targets (its base). It also returns whether the pull request is a draft, GitHub’s merge state, the number of commits the branch is ahead of the base, and the number of commits the base has gained since the branch split off. The last field is the total, failing and pending checks on the latest commit of the branch. pr_context caches its result for 60 seconds.

pr_context never raises. When there is no open pull request, no GitHub remote or no token, or when GitHub refuses the request, pr is None and note gives the reason. The example below runs _checks, the function that counts checks, against a fake API.

These are the main entry points. All of them except gh_record_deploy are also gheasy commands. They read and write .gheasy/config.json, and most print the next step.

Repository health

gh_check audits a repository against gheasy’s defaults and returns a list of findings. In the checkout it looks for gheasy’s pre-commit hook, for the LFS block in .gitattributes, and, when a pyproject.toml exists, for a hatchling build. With a token it also asks GitHub whether the repository has topics and a .github/dependabot.yml. When the GitHub request fails, gh_check adds a warn finding in the branch-protection category with the error. local=False and remote=False skip either group.

gh_apply runs the fix of every finding that has one and is not ok. It returns the findings it fixed. dry_run=True lists the fixes without running them. confirm=True asks before each fix. The local findings have fixes. The GitHub findings only suggest a command to run.

RepoFinding

Each finding is a RepoFinding. Its fields are level (ok, warn or error), category (such as hooks or lfs), message, fix (a function that fixes the problem, or None), cmd_repr (the command the fix stands for) and docs (a documentation link). Printing a finding shows a tick, a warning sign or a cross, then the category, the message and the suggested command. apply runs the fix. When there is no fix, apply prints the suggested command.

GheasyRepo

GheasyRepo holds a GitHub repository (ref), a token and a local path. It runs the functions above with them. Creating one makes no API calls. It parses ref, which is an owner/repo string or a GitHub URL, and raises ValueError when it cannot parse ref. A local path in ref is not a supported form. Pass the path in path. check and apply are gh_check and gh_apply for that repository. create makes the repository on GitHub. It creates the repository under an organisation when the owner is not the signed-in user.

GheasyRepo.new scaffolds a whole project in one call. It runs these steps in order:

  1. Creates the GitHub repository.
  2. Clones it into parent_dir, or skips the clone when the folder is already a Git repository.
  3. Pins the Python version with uv python pin.
  4. Runs nbdev-new when the template is nbdev.
  5. Converts pyproject.toml to hatchling.
  6. Sets up LFS with the default patterns.
  7. Installs the nbdev pre-commit hook.
  8. Writes the config and the workflow when you pass workflows.
  9. Commits and pushes the initial changes in one commit and one push.
  10. Sets repository topics when you pass topics.

The gheasy gh-new command calls it.
