Repository management

Read and change a local Git repository from Python, with a way to undo any change that could lose work.

Classifying commands

The gateway has to know whether a command reads or writes before it can choose a lock. classify sorts a Git argument list into one of three kinds. read commands, such as status and log, share a lock and run with --no-optional-locks, which stops Git from rewriting its index file in passing. write commands take the lock alone. net commands (clone, fetch, ls-remote and push) use a separate lock.

Some commands read or write depending on their arguments: git branch --list reads but git branch -d x writes. The MIXED table lists, for each such command, the arguments that make it a read. With no arguments, branch, remote and tag read, and the other commands in MIXED write. symbolic-ref reads unless it has more than one non-option argument. classify skips leading global options such as -c name=value and -C path before it reads the command name. A command classify does not recognise counts as a write. An unknown command that changes the repository therefore never runs alongside another command. The cost is some lost concurrency.

Locking one repository

RepoLock is a readers-writer lock: any number of readers at once, or one writer alone. The thread holding the write lock can take it again and can also read. A change can therefore inspect its own result without waiting on itself. A thread that holds a read lock cannot take the write lock. It waits for its own read to end and never proceeds. The net lock is separate because network commands do not touch the index or the working tree. It is reentrant and lets one thread at a time run a network command.

Recovery state

A Safepoint records where a repository was just before one change: the commit HEAD pointed at, the current branch, the commit holding a snapshot of uncommitted work (empty when there was none), how many files were uncommitted (dirty, which also counts untracked files), the token, which is the identifier you pass to undo to select this safepoint, and the time. Git keeps each safepoint commit reachable through refs under refs/leela/safepoint/. A ref is a name that Git resolves to a commit, such as a branch name, a tag name or a commit id. The module also lists safepoints in a journal file inside .git. An ordinary push sends neither the refs nor the journal. Safepoints stay on your machine. describe returns one line such as merge on main, 2 uncommitted file(s) kept.

SAFEPOINT_REF and JOURNAL_NAME still say leela, the editor this module was written for. Renaming them would lose track of safepoints already on disk.

FOREIGN_LOCK matches the errors Git prints when another process, such as a terminal or another editor, is holding one of Git’s lock files. The gateway retries those commands. The section “Running a command” gives the retry rules.

The Git gateway

GitGateway runs Git commands under the right repository lock. The locks protect a repository only when every caller shares one gateway. Call gateway() to get the process-wide instance. Do not create your own. The checks on this page create private gateways only so they can test them.

The gateway also caches values that change less often than the files. memo(cwd, key, make, ttl=60) caches the value make() returns, per repository and key, for ttl seconds. env_for is an attribute you can set to a function that takes a checkout folder and returns the environment variables Git runs with there. An application can use it to put the project’s virtual environment on PATH. Git then finds a filter program installed there. env(cwd, ttl=30) returns that environment, cached for ttl seconds. When env_for is None, Git inherits the process’s environment. resolves(cwd, command) returns the full path of the program a filter or hook command would run, searching that PATH, or an empty string when none is found.

net_env(cwd) is the environment for a command that talks to a remote: clone, fetch, ls-remote, push and pull. When GITHUB_TOKEN or GH_TOKEN is set and gh has a keyring login for github.com, net_env removes the two token variables. The gh auth git-credential helper then uses the keyring login. Before, a token that was not valid any more stopped every push with Invalid username or token, although gh had a good login. gh_keyring(cwd) runs gh auth status without the token variables and caches the answer for five minutes. In all other cases net_env returns env(cwd) unchanged. os.environ never changes.

Running a command

GitGateway.run is the only function in this module that starts Git. It takes the lock classify chooses, or the one named by kind. When Git fails because another process holds one of its lock files, run retries the command. These constants set the limits:

Setting Name Value
Default timeout timeout 30 seconds
Maximum attempts LOCK_ATTEMPTS 4
Delay before the first retry LOCK_BACKOFF 0.15 seconds
Delay multiplier for each later retry none 2

A failed command raises GitError, with both stderr and stdout in the message because Git prints useful text on either. With check=False it returns the failed result instead. A command that exceeds timeout seconds raises GitError even with check=False. run raises GitError when Git is not on PATH. out is run returning only stdout. Git’s stdin is input when given and /dev/null otherwise. Git never reads from the caller’s terminal.

Recording recovery points

The journal is a JSON file inside .git that lists safepoints newest first, keeping the latest JOURNAL_KEEP (60). It is written to a temporary file and renamed into place. A reader never sees half a file. A journal that cannot be read or written never stops a Git command. A journal that cannot be read counts as empty.

Creating a safepoint

safepoint captures uncommitted work with git stash create, which builds a stash commit without touching your files or adding to the stash list. git stash create leaves out untracked files, so a safepoint does not hold them. The dirty count still includes untracked files, because it comes from git status --porcelain. safepoint then points refs at the stash commit and at HEAD. Git’s garbage collection keeps both commits. It returns None on a branch with no commits yet, where there is nothing to return to. transaction holds the repository’s write lock for a whole operation and records the safepoint before the operation starts. With snapshot=False it records none and yields None.

Restoring a safepoint

undo first aborts any merge, rebase, cherry-pick or revert in progress. It then switches back to the recorded branch, resets it to the recorded commit, and reapplies the saved uncommitted work. Without a token it restores the newest safepoint. It returns a dictionary with the keys token, op, head, branch, restored and describe. restored is the number of tracked files in the stashed work when undo reapplied a stash, and 0 otherwise. It can be lower than the dirty count recorded in the safepoint, because dirty includes untracked files and the stash does not contain them. undo raises GitError when the repository has no safepoint or when token matches none.

If the saved work no longer applies cleanly, undo raises GitError after HEAD is already reset. The work stays reachable as a commit, and the message gives the git stash apply command that recovers it. undo never discards that work. active_operation names the operation in progress, or returns an empty string.

Parsing conflict markers

When Git cannot combine two changes to the same lines, it writes both into the file between conflict markers: <<<<<<< opens the block, ======= separates our side from theirs, and >>>>>>> closes it. _conflict_blocks finds each complete block and returns one dictionary per block. The keys start and end are character offsets into the text, and end is just past the line that closes the block. The keys ours and theirs hold the text of each side. A marker sequence with a part missing is left as ordinary text.

block, = _conflict_blocks('a\n<<<<<<< HEAD\nx\n=======\ny\n>>>>>>> o\nb\n')
test_eq((block['ours'], block['theirs']), ('x\n', 'y\n'))
test_eq(block['start'], 2)

test_eq(_conflict_blocks('nothing here\n'), [])
test_eq(_conflict_blocks('<<<<<<< HEAD\nx\nno middle\n'), [])       # malformed stays text
test_eq(_conflict_blocks('<<<<<<< HEAD\nx\n=======\ny\n'), [])      # no closing marker
test_eq(len(_conflict_blocks('<<<<<<< a\n1\n=======\n2\n>>>>>>> b\n'
                             '<<<<<<< a\n3\n=======\n4\n>>>>>>> b\n')), 2)
test_eq(_conflict_blocks('<<<<<<< a\n\n=======\n\n>>>>>>> b\n')[0]['ours'], '\n')

Short-lived status caching

An editor’s file tree can ask for the status of the same repository several times in one refresh. _cached shares one answer for _CACHE_TTL seconds, which is 0.45. GitRepo.decorations, info and brief use it. invalidate(root) drops every cached answer for a repository, and each method that changes the repository calls it. An answer that was still being worked out when invalidate ran is not stored. A stale result cannot re-enter the cache. GitRepo.changes, which an editor calls right after saving a file, never uses the cache.

Preserving uncommitted work

Some operations need a clean working tree. _set_aside snapshots the changes to tracked files, keeps the snapshot under AUTOSTASH_REF, and runs git reset --hard. It returns the snapshot commit, or an empty string when no tracked file had changes. _bring_back reapplies the snapshot after the operation. It first tries to restore the staged state as well, and then tries the plain files alone.

The ref keeps the snapshot reachable. Nothing is lost when _bring_back cannot reapply it. In that case _bring_back leaves the operation’s result in place and returns a note with the command that recovers the work. It returns an empty string when the work went back.

test_eq((r.root/'readme.md').read_text(), 'mine\n')     # ...and the work comes back

A merge that stops on conflicts has done its job, and a person then resolves the conflicts. _attempt therefore returns the command’s output, and does not raise, when the command leaves conflicts or an operation in progress. Switching branches

checkout switches to a local branch or a remote branch such as origin/feature. For a remote branch it creates a local branch that tracks it, or switches to the existing one and sets its upstream.

Git refuses to switch when the switch would overwrite uncommitted changes. checkout then sets the changes aside, switches, and puts them back. If they conflict with what is on the target branch, checkout switches back, restores the work and raises GitError. The repository is then on the original branch with the work in place. checkout raises GitError for an empty branch name. Any other refusal from Git is raised unchanged. A successful checkout returns the dictionary described under “Mutation results” and records a safepoint first.

Bringing work together

merge, rebase, cherry_pick, revert and reset are all guarded. A conflict comes back as a result, not an exception. The result lists the conflicted files, and the operation stays in progress. merge takes a strategy: merge, squash (stage the combined changes without committing them) or ff-only. A unified diff is made of hunks, separate blocks that each start with an @@ line. _patch_hunks splits one file’s diff into its hunks and returns one record for each hunk. Replaying a branch in memory

A rebase rewrites history. _replay shows what a rebase would do without rewriting anything. It merges each of your commits onto the previous result with git merge-tree and wraps the result in a new commit with git commit-tree. Both commands only add objects to Git’s object store. They touch no branch, index or working tree. _replay stops at the first commit that would conflict, which is where a real rebase would stop. It returns three values: the commit it stopped at (oid and subject, or None), the number of commits replayed, and the conflicted files.

SYNC_OPS names the four ways sync can bring a branch level with its upstream. REMOTE_OPS names the three commands that talk to a remote. STATE_KEYS lists eight keys of the info dictionary: root, branch, upstream, ahead, behind, clean, branches and changes. _short_commits formats up to 20 commits as short subject lines. _said returns the summary or message of a result dictionary, or the stripped text of any other value. _upstream returns the upstream you name, or the one the branch tracks, and raises GitError when there is neither.

test_eq(_short_commits([{'short': 'abc1234', 'subject': 'a subject'}]), ['abc1234 a subject'])
test_eq(_short_commits([{'short': 'a', 'subject': 'x'}] * 30), ['a x'] * 20)   # capped for a summary
test_eq(_said({'summary': 's'}), 's')
test_eq(_said({'message': 'm'}), 'm')
test_eq(_said(' text '), 'text')
test_eq(_said(None), '')
test_eq(sorted(SYNC_OPS), ['fast-forward', 'merge', 'rebase', 'reset'])
test_eq(REMOTE_OPS, ('fetch', 'pull', 'push'))

r = GitRepo.at(mkrepo({'a.txt': 'base\n'}))
test_fail(lambda: r._upstream(), contains='tracks nothing')
sh(r.root, 'branch', 'other')
commit(r.root, 'ours', b__txt='b\n')
onto = r._ask('rev-parse', 'HEAD')
r.checkout('other')
commit(r.root, 'theirs', c__txt='c\n')

test_eq((stops, replayed, files), (None, 1, []))        # replays cleanly
test_eq(r._ask('rev-parse', 'HEAD'), head)              # ...and moved nothing

sh(c.root, 'branch', 'other')

Choosing a synchronization strategy

divergence(upstream='', fetch=False) compares the current branch with its upstream, or with a branch you name, and relation says how they stand: identical, ahead, behind or diverged. With fetch=True it fetches first. It raises GitError when the branch tracks nothing and you name no upstream, and when the two share no merge base. The counts ahead and behind are exact however many commits there are, while ours and theirs list at most 20 commits each.

divergence then rehearses each way of bringing the branch level. A fast-forward is possible when you have no commits of your own. A merge or a reset is possible whenever the upstream has commits you lack. A rebase is possible when both sides have commits. The merge is rehearsed with merge-tree and the rebase with _replay. The merge and rebase options list the files they would conflict on. The options that rewrite history, rebase and reset, are marked destructive.

recommended is a fast-forward when you have no commits of your own. When both sides have commits, it is a rebase if your commits replay without conflict and no tracked file has uncommitted changes. Otherwise it is a merge. It is empty when the upstream has nothing you lack.

Ignore rules a folder needs

A folder without a suitable .gitignore stages build output such as target/, dist/, __pycache__ and node_modules along with the work. IGNORE_KINDS describes four kinds of project: Rust, maturin (a Python package built from Rust), Python and Node. For each it lists the files that mark a folder as that kind, paths that must end up ignored, and the rules to add when they are not. project_kinds returns the kinds a folder holds. A folder holds maturin when it has both pyproject.toml and Cargo.toml. A folder holds any other kind when it has any one of that kind’s marker files. A maturin folder is not also listed as python.

prepare_ignores adds the missing rules to the folder’s own .gitignore, not the one at the repository’s root. A root rule /target/ does not match crate/target/, so rules written there for a crate in a subfolder would ignore nothing. A crate that carries its own ignore file also keeps it when moved into another repository. write=False reports what it would add without writing. prepare_ignores returns a dictionary with kinds (the kinds that lacked rules), added (the lines written, or the lines it would write when write=False) and path (the .gitignore file). It skips lines that are already in the file, and added is empty when the rules are already there. That is the usual case on a second run.
