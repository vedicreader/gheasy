Repository management

Read and change a local Git repository from Python, with a way to undo any change that could lose work.

Classifying commands

The gateway has to know whether a command reads or writes before it can choose a lock. classify sorts a Git argument list into one of three kinds. read commands, such as status and log, share a lock and run with --no-optional-locks, which stops Git from rewriting its index file in passing. write commands take the lock alone. net commands (clone, fetch, ls-remote and push) use a separate lock.

Some commands read or write depending on their arguments: git branch --list reads but git branch -d x writes. The MIXED table lists, for each such command, the arguments that make it a read. A command classify does not recognise counts as a write. That costs a little concurrency, but it means an unknown command that changes the repository never runs alongside another.

Locking one repository

RepoLock is a readers-writer lock: any number of readers at once, or one writer alone. The thread holding the write lock can take it again and can also read, so a change can inspect its own result without waiting on itself. The net lock is separate because network commands do not touch the index or the working tree.

source

RepoLock

def RepoLock():

A per-repository readers-writer lock, reentrant for the thread holding the write.

lock = RepoLock()
with lock.read():
    with lock.read(): pass                              # readers do not exclude each other
with lock.write():
    with lock.write(): pass                             # the writing thread is reentrant
    with lock.read(): pass                              # ...and may read inside its own write

seen = []
def reader():
    with lock.read(): seen.append('read')
with lock.write():
    t = threading.Thread(target=reader); t.start(); t.join(.2)
    test_eq(seen, [])                                   # a writer excludes a reader in another thread
t.join(2)
test_eq(seen, ['read'])

held = threading.Event()
def netter():
    with lock.net(): held.set(); time.sleep(.05)
t = threading.Thread(target=netter); t.start()
held.wait(2)
with lock.read(): pass                                  # ...but the network lock does not
t.join(2)

Recovery state

A Safepoint records where a repository was just before one change: the commit HEAD pointed at, the current branch, the commit holding a snapshot of uncommitted work (empty when there was none), how many files were uncommitted, the token that names it, and the time. Safepoints are kept as refs under refs/leela/safepoint/ and listed in a journal file inside .git. An ordinary push does not send either, so they stay on your machine. describe returns one line such as merge on main, 2 uncommitted file(s) kept.

SAFEPOINT_REF and JOURNAL_NAME still say leela, the editor this module was written for. Renaming them would lose track of safepoints already on disk.

FOREIGN_LOCK matches the errors Git prints when another process, such as a terminal or another editor, is holding one of Git’s lock files. The gateway retries those commands a few times, with a growing pause, before it gives up.

The Git gateway

GitGateway runs Git commands under the right repository lock. The locks only protect anything if every caller shares one gateway, so use gateway() to get the process-wide instance rather than creating your own. The checks on this page create private gateways only so they can test them.

The gateway also caches, for some seconds, values that change less often than the files. memo(cwd, key, make, ttl) caches any value per repository. env_for lets an application choose the environment variables Git runs with in each checkout, for example to put the project’s virtual environment on PATH so Git can find a filter program installed there. When env_for is None, Git inherits the process’s environment. resolves finds the program a filter or hook command would run, using that PATH.

Running a command

GitGateway.run is the only function in this module that starts Git. It takes the lock classify chooses, or the one named by kind, and runs the command with a 30 second timeout by default. When Git fails because another process holds one of its lock files, run tries again, up to four times in all, with a growing pause between tries. A failed command raises GitError, with both stderr and stdout in the message because Git prints useful text on either. With check=False it returns the failed result instead. out is run returning only stdout. Git’s stdin is input when given and /dev/null otherwise, so Git never shares the caller’s terminal.

Recording recovery points

The journal is a JSON file inside .git that lists safepoints newest first, keeping the latest JOURNAL_KEEP (60). It is written to a temporary file and renamed into place, so a reader never sees half a file. A journal that cannot be read or written never stops a Git command; one that cannot be read counts as empty.

Creating a safepoint

safepoint captures uncommitted work with git stash create, which builds a stash commit without touching your files or adding to the stash list. It then points refs at that commit and at HEAD, so Git’s garbage collection keeps both. It returns None on a branch with no commits yet, where there is nothing to return to. transaction holds the repository’s write lock for a whole operation and records the safepoint before the operation starts.

Restoring a safepoint

undo first aborts any merge, rebase, cherry-pick or revert in progress. It then switches back to the recorded branch, resets it to the recorded commit, and reapplies the saved uncommitted work. Without a token it restores the newest safepoint.

If the saved work no longer applies cleanly, undo raises GitError, but the work stays reachable as a commit and the message gives the git stash apply command that recovers it. undo never discards that work. active_operation names the operation in progress, or returns an empty string.

gateway() returns the process-wide GitGateway.

Parsing conflict markers

When Git cannot combine two changes to the same lines, it writes both into the file between conflict markers: <<<<<<< opens the block, ======= separates our side from theirs, and >>>>>>> closes it. _conflict_blocks finds each complete block and returns where it starts and ends and the text of both sides. A marker sequence with a part missing is left as ordinary text.

block, = _conflict_blocks('a\n<<<<<<< HEAD\nx\n=======\ny\n>>>>>>> o\nb\n')
test_eq((block['ours'], block['theirs']), ('x\n', 'y\n'))
test_eq(block['start'], 2)

test_eq(_conflict_blocks('nothing here\n'), [])
test_eq(_conflict_blocks('<<<<<<< HEAD\nx\nno middle\n'), [])       # malformed stays text
test_eq(_conflict_blocks('<<<<<<< HEAD\nx\n=======\ny\n'), [])      # no closing marker
test_eq(len(_conflict_blocks('<<<<<<< a\n1\n=======\n2\n>>>>>>> b\n'
                             '<<<<<<< a\n3\n=======\n4\n>>>>>>> b\n')), 2)
test_eq(_conflict_blocks('<<<<<<< a\n\n=======\n\n>>>>>>> b\n')[0]['ours'], '\n')

Short-lived status caching

An editor’s file tree can ask for the status of the same repository several times in one refresh. _cached shares one answer for _CACHE_TTL seconds, under half a second. invalidate(root) drops every cached answer for a repository, and each method that changes the repository calls it. An answer that was still being worked out when invalidate ran is not stored, so a stale result cannot slip back into the cache. changes, which an editor calls right after saving a file, never uses the cache.

Reporting outcomes

Every guarded change returns the same dictionary, described under “Mutation results” below, and _summarise turns it into one sentence for a person. A conflict comes first, because it is what needs dealing with, then an operation still in progress, then files staged but not yet committed.

_explain_filters explains filters that cannot run. A filter is a program, named in .gitattributes, that Git runs on a file as it is staged and checked out; nbstripout, which strips outputs from notebooks, is a common one.

base = {'op': 'merge', 'staged': [], 'conflicted': [], 'moved': False, 'head': 'abc1234',
        'message': '', 'operation': {'active': ''}}
test_eq(_summarise(base), 'merge changed nothing')
test_eq(_summarise(base | {'moved': True}), 'merge moved this branch to abc1234')
test_eq(_summarise(base | {'staged': ['a']}), 'merge staged 1 file without committing -- commit to finish')
test_eq(_summarise(base | {'operation': {'active': 'rebase'}}),
        'rebase is in progress -- continue, skip, or abort it')
test_eq(_summarise(base | {'conflicted': ['a', 'b']}),
        'merge stopped at 2 conflicted files -- resolve them to continue')
test_eq(_summarise(base | {'message': 'Already up to date.\nmore'}), 'Already up to date.')
# a conflict outranks everything else, because it is what the person has to deal with
test_eq(_summarise(base | {'conflicted': ['a'], 'staged': ['a'], 'moved': True}),
        'merge stopped at 1 conflicted file -- resolve them to continue')

Reading a diff

Git’s machine-readable diff output separates fields with NUL characters and writes a renamed file as three fields rather than two, which a simple two-field parse gets wrong. _diff_status and _diff_numstat handle renames, and both keep None line counts for a binary file rather than reporting zero lines changed. _unified makes a unified diff of two strings, for files Git has no earlier version of.

test_eq(_unified_arg(3), '--unified=3')
test_eq(_unified_arg(-1), '--unified=0')                # clamped both ways
test_eq(_unified_arg(999), '--unified=20')

d = _unified('a\n', 'b\n', 'a/x', 'b/x')
assert d.startswith('--- a/x') and '-a' in d and '+b' in d
test_eq(_unified('same\n', 'same\n', 'a', 'b'), '')

rows = _diff_status('M\0a.py\0R090\0old.py\0new.py\0A\0c.py\0')
test_eq([r['path'] for r in rows], ['a.py', 'new.py', 'c.py'])
test_eq(rows[1]['old_path'], 'old.py')
test_eq((rows[1]['status'], rows[1]['similarity']), ('R', 90))
test_eq(rows[0]['similarity'], 0)
test_eq(_diff_status(''), [])

Preserving uncommitted work

Some operations need a clean working tree. _set_aside snapshots the changes to tracked files, keeps the snapshot under AUTOSTASH_REF, and resets the tree. _bring_back reapplies the snapshot after the operation.

Because the ref keeps the snapshot reachable, nothing is lost when it cannot be reapplied. In that case _bring_back leaves the operation’s result in place and returns a note with the command that recovers the work.

test_eq((r.root/'readme.md').read_text(), 'mine\n')     # ...and the work comes back

Mutation results

A merge that stops on conflicts has done its job; a person now resolves them. So _attempt returns normally when a command leaves conflicts or an operation in progress, and raises GitError for any other failure. _guarded wraps one risky change: it takes the write lock, records a safepoint, sets uncommitted work aside when asked, runs the change, brings the work back, and builds the result with _outcome.

That result is the dictionary every guarded method returns. It holds the operation’s name, Git’s message, the new and the old HEAD, whether the branch moved, the branch, the staged and conflicted files, any operation in progress, whether uncommitted work was carried across, the undo token with a description of what it undoes, and a one-sentence summary.

Replaying a branch in memory

A rebase rewrites history, so the only reliable way to know what one would do is to do it somewhere that does not count. _replay merges each of your commits onto the previous result with git merge-tree and wraps the result in a new commit with git commit-tree. Both only add objects to Git’s store and touch no branch, index or working tree, so the rehearsal leaves nothing you can see. It stops at the first commit that would conflict, which is where a real rebase would stop.

SYNC_OPS names the four ways sync can bring a branch level with its upstream, and REMOTE_OPS the three commands that talk to a remote.

test_eq(_said(None), '')
test_eq(sorted(SYNC_OPS), ['fast-forward', 'merge', 'rebase', 'reset'])
test_eq(REMOTE_OPS, ('fetch', 'pull', 'push'))

Choosing a synchronization strategy

divergence compares the current branch with its upstream, or with a branch you name, and relation says how they stand: identical, ahead, behind or diverged. It then rehearses each way of bringing the branch level. A fast-forward is possible when you have no commits of your own, a merge or a reset whenever the upstream has commits you lack, and a rebase when both sides have commits. The merge is rehearsed with merge-tree and the rebase with _replay, so each option lists the files it would conflict on, and the options that rewrite history are marked destructive.

recommended is a fast-forward when you have no commits of your own. When both sides have commits, it is a rebase if your commits replay without conflict and nothing is uncommitted, and a merge otherwise. It is empty when the upstream has nothing you lack.
